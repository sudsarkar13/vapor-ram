# Release Manager Skill

> **ACTIVATION RULE**: Only run this when the maintainer explicitly asks for a release
> or version bump. Do not auto-trigger for routine edits or bug fixes.

Releases are **tag-driven**. You prepare the commit; pushing an annotated tag runs
[.github/workflows/release.yml](../../.github/workflows/release.yml), which does the
building, publishing and uploading. There are no manual `gh release create` or
`twine upload` steps any more — running them by hand risks double-publishing.

---

## 📌 Versioning & Channels

| Channel | Tag format | GitHub Release | PyPI | Docs synced |
| :-- | :-- | :-- | :-- | :-- |
| **Stable** | `v1.0.7` | latest release | published | yes |
| **Release Candidate** | `v1.0.7-rc.1` | prerelease | published | no |
| **Beta** | `v1.0.7-beta.1` | prerelease | published | no |
| **Alpha** | `v1.0.7-alpha.3` | prerelease | published | no |

Release titles are generated by the pipeline as `<tag> — <Channel> Release`
(e.g. `v1.0.7-beta.1 — Beta Release`). Do not hand-write verbose titles.

PyPI normalises prerelease versions (`1.0.7-alpha.3` → `1.0.7a3`), so prereleases
require `pip install --pre vapor-ram`.

## 📋 Standard Operating Procedure

### 1. Bump the version everywhere (one command)

All eight manifests must agree or CI fails. Use the checker rather than editing by hand:

```bash
python3 tools/check_version.py --set 1.0.7-beta.1
python3 tools/check_version.py            # verify they now agree
```

Covered files: `vapor_ram/version.py`, `setup.py`, `pyproject.toml`,
`vapor_ram/openai_server.py`, `c/vapor_engine.c`, `tools/package_release.py`,
`tools/download_model.py`. The CLI banner reads `__version__`, so it needs no bump.
`vapor`, `c/vapor_engine.c`, `tools/package_release.py`, `tools/download_model.py`.

### 2. Rebuild the dashboard and the C engine

`web/dist` is committed and served directly by the Python package, so a stale build
ships a stale UI. CI fails if the committed `web/dist` doesn't match a fresh build.

```bash
yarn --cwd web install --immutable
yarn --cwd web build      # regenerates web/dist
make -C c                 # rebuilds c/vapor_engine
```

### 3. Run the test suite

```bash
python3 tests/test_engine.py
```

All checks must pass. The suite covers the telemetry contract, context-window
honesty, model-directory isolation, preset resolution, concurrency and the
weightless failure mode.

### 4. Write the changelog and release notes

Both are **required by the pipeline** — the release fails if either omits the version.

`CHANGELOG.md` — prepend a section (the heading must contain `[vX.Y.Z]`):

```markdown
## [v1.0.7-beta.1] - YYYY-MM-DD

### 🐛 Fixed Bugs & Issues
- ...

### 🚀 Highlights & Features
- ...
```

`RELEASE_NOTES.md` — replace the contents with the delta for **this version only**
(never paste the full changelog):

```markdown
# v1.0.7-beta.1 — Beta Release

## 🔄 What's Changed (v1.0.7-alpha.3 ➔ v1.0.7-beta.1)
- **Channel**: Beta Release

### 🐛 Fixed Bugs & Issues
- ...

### ✨ New Features & Enhancements
- ...
```

The pipeline appends the channel badge and install command automatically.

### 5. Commit and push

```bash
git add -A
git commit -m "Release v1.0.7-beta.1: <one-line summary>"
git push origin main
```

Wait for [CI](../../.github/workflows/ci.yml) to pass on `main` before tagging.

### 6. Tag — this triggers the release

```bash
git tag -a v1.0.7-beta.1 -m "v1.0.7-beta.1 — Beta Release"
git push origin v1.0.7-beta.1
```

The pipeline then:

1. **validate** — parses the channel from the tag, asserts every manifest declares
   that exact version, and requires matching `CHANGELOG.md` / `RELEASE_NOTES.md` entries.
2. **verify** — builds the C engine and runs the full test suite on Linux and macOS.
3. **tarballs** — builds `vapor-ram-v<version>-linux-x86_64.tar.gz` and
   `-macos.tar.gz` natively on each runner.
4. **build-dist** — builds the sdist and wheel, runs `twine check`, and asserts the
   artifact version matches the tag.
5. **github-release** — creates the release with the correct prerelease flag; only
   Stable is marked `--latest`.
6. **pypi-publish** — uploads via OIDC Trusted Publishing with PEP 740 attestations.
   No API token is stored.
7. **docs** — for Stable only, rewrites the version links in `docs/index.html` and
   pushes, refreshing GitHub Pages.

### 7. Verify

```bash
gh release view v1.0.7-beta.1 --repo sudsarkar13/vapor-ram
pip index versions vapor-ram --pre
```

## 🔁 Re-running a failed release

The workflow is idempotent: it updates an existing release rather than erroring.
Re-run it from the Actions tab, or:

```bash
gh workflow run release.yml -f tag=v1.0.7-beta.1
# add -f skip_pypi=true if that version already uploaded successfully
```

PyPI refuses re-uploads of an existing version — use `skip_pypi` when only the
GitHub Release needs repairing.

## 📦 Packaging notes

Python modules live in `vapor_ram/`. Runtime assets (dashboard, presets, tools,
compiled engine) live at the repository root and are staged into the package at
build time by `setup.py`'s `build_py` override — they are **not** committed under
`vapor_ram/` and are gitignored there.

Both the sdist and the wheel are gated in CI for completeness. After any change
to the packaging, verify a real install rather than trusting the build log:

```bash
python -m build --wheel
pip install --force-reinstall dist/*.whl
vapor --version && vapor presets      # must list the disk-defined personas
vapor serve --port 8901 &             # then curl the dashboard and a JS chunk
```
