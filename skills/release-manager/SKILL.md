# Release Manager Skill

> **ACTIVATION RULE**: Only run this when the maintainer explicitly asks for a release
> or version bump. Do not auto-trigger for routine edits or bug fixes.

Releases are **tag-driven**. You prepare the commit; pushing an annotated tag runs
[.github/workflows/release.yml](../../.github/workflows/release.yml), which does the
building, publishing and uploading. There are no manual `gh release create` or
`twine upload` steps any more — running them by hand risks double-publishing.

---

## 📌 Versioning & Channels

| Channel | Tag format | GitHub Release | PyPI | Docs synced |
| :-- | :-- | :-- | :-- | :-- |
| **Stable** | `v1.0.7` | latest release | published | **yes** |
| **Release Candidate** | `v1.0.7-rc.1` | prerelease | published | no |
| **Beta** | `v1.0.7-beta.1` | prerelease | published | no |
| **Alpha** | `v1.0.7-alpha.3` | prerelease | published | no |

### The documentation site advertises stable only

**The GitHub Pages site must never name an alpha, beta or RC as its version.**
The `docs` job is gated on `channel == 'stable'`, so publishing a prerelease
leaves the site untouched — that gate is the whole mechanism. Do not add a
prerelease branch to it, and do not hand-edit a prerelease version into the
pages.

This is a rule about what the site **advertises**, never about what users may
**take**:

- `docs/releases.html` and `docs/changelog.html` read the GitHub API live and
  list **every** release, prereleases included, with a filter to isolate them.
  Anyone who wants an untested build can download it or `pip install` it by
  exact version. There is no gating, and none should be added.
- Only the version badge in the page navigation is stable-pinned.

Every version-bearing string on the three pages is wrapped in
`<!--VERSION-->…<!--/VERSION-->` markers, which the `docs` job rewrites. After
rewriting it greps all three pages and **fails the release** if any string
matching `v1.x.y[-channel.n]` other than the tag survives. So:

- Never hard-code a version into `docs/*.html` outside the markers. The nav tag
  on `releases.html` and `changelog.html` was hard-coded once and silently
  drifted three versions behind `index.html`.
- Never write a literal example version into page comments or copy either — the
  guard cannot tell a comment from a claim, and will fail the release. Write
  `<version>` instead.

Release titles are generated by the pipeline as `<tag> — <Channel> Release`
(e.g. `v1.0.7-beta.1 — Beta Release`). Do not hand-write verbose titles.

PyPI normalises prerelease versions (`1.0.7-alpha.3` → `1.0.7a3`). Pinning an
exact prerelease works without any flag (`pip install vapor-ram==1.0.7a3`);
`--pre` is only needed to let pip *resolve* to a prerelease on its own.

## 📋 Standard Operating Procedure

### 1. Bump the version everywhere (one command)

All eight manifests must agree or CI fails. Use the checker rather than editing by hand:

```bash
python3 tools/check_version.py --set 1.0.7-beta.1
python3 tools/check_version.py            # verify they now agree
```

Covered files (**seven**, and the checker is the source of truth — see
`TARGETS` in [tools/check_version.py](../../tools/check_version.py)):
`vapor_ram/version.py`, `setup.py`, `pyproject.toml`,
`vapor_ram/openai_server.py`, `c/vapor_engine.c`, `tools/package_release.py`,
`tools/download_model.py`.

The CLI banner reads `__version__`, so it needs no bump. `README.md` and the
docs pages deliberately carry no hard-coded version: the README uses
`v<version>` placeholders and the pages use the markers above.

### 2. Rebuild the dashboard and the C engine

`web/dist` is committed and served directly by the Python package, so a stale build
ships a stale UI.

```bash
yarn --cwd web install --immutable
yarn --cwd web build      # regenerates web/dist — commit the result
make -C c                 # builds c/vapor_engine and c/simd_bench — do NOT commit
```

CI runs [tools/check_web_dist.py](../../tools/check_web_dist.py), which verifies
every asset `index.html` references exists on disk. It deliberately does **not**
diff against a fresh build: Turbopack chunk names are content-addressed per
build and are not reproducible, so an equality check would fail even when
nothing changed. That means a stale-but-internally-consistent `web/dist` will
pass CI — rebuilding after any `web/` change is on you.

**The compiled binaries are not tracked.** `c/vapor_engine` and `c/simd_bench`
were committed until v1.0.7, which pushed one host's architecture at every
other host. They are gitignored now; `setup.py` runs `make -C c` at install
time and `MANIFEST.in` ships the sources. Build them locally to run the tests,
but never `git add -f` them.

### 3. Run the test suite

```bash
python3 tests/test_engine.py
```

All checks must pass (164 as of v1.0.7). The suite covers the telemetry
contract, context-window honesty, model-directory isolation, preset resolution,
concurrency, the weightless failure mode, reasoning, network sharing — and a
**stable-release honesty** group that guards against regressions in what the
software claims about itself.

The suite writes config through `VAPOR_CONFIG_PATH` so it cannot touch your real
`vapor.json`, which is untracked (see `vapor.example.json` for the reference
copy).

### 4. Every user-visible number must be measured

**The standing rule for this project: show real values, or show nothing.** No
figure that reaches a user — README, docs site, dashboard, CLI output — may be
an estimate presented as a measurement, and no command may print a PASS/FAIL
against a target it has not actually checked.

The v1.0.7 audit found four commands violating this, including `vapor bench`,
which reported the project's headline 1.5 GB RAM ceiling as **met** using the
RSS of a process that had failed to start. `vapor plan`, `vapor inspect` and
`vapor doctor` each did a version of the same thing, and the SIMD benchmark
reported ~200,000 GFLOPS because `-O3` had deleted its timing loops.

Before a release that touches any user-visible figure:

```bash
vapor bench            # O_DIRECT streaming throughput on the real GGUF blocks
vapor bench --simd     # scalar vs AVX2 dot product
vapor inspect          # GGUF geometry, with an integrity check
vapor plan             # design budget vs measured RSS
vapor doctor           # host capability
```

Re-measure rather than copying figures from a previous release — throughput
moves with machine load and thermal state. Quote the host alongside the numbers
(the README's reference machine is a Ryzen 7 5700U, 8c/16t, 15 GB, NVMe). If
something cannot be measured, say so instead of estimating.

The `test_stable_release_honesty` group in
[tests/test_engine.py](../../tests/test_engine.py) pins each corrected claim, so
a regression fails the suite rather than shipping. **Extend that group whenever
a release adds a user-visible number.**

### 5. Write the changelog and release notes

Both are **required by the pipeline** — the release fails if either omits the version.

`CHANGELOG.md` — prepend a section (the heading must contain `[vX.Y.Z]`):

```markdown
## [v1.0.7-beta.1] - YYYY-MM-DD

### 🐛 Fixed Bugs & Issues
- ...

### 🚀 Highlights & Features
- ...
```

`RELEASE_NOTES.md` — replace the contents with the delta for **this version only**
(never paste the full changelog):

```markdown
# v1.0.7-beta.1 — Beta Release

## 🔄 What's Changed (v1.0.7-alpha.3 ➔ v1.0.7-beta.1)
- **Channel**: Beta Release

### 🐛 Fixed Bugs & Issues
- ...

### ✨ New Features & Enhancements
- ...
```

The pipeline appends the channel badge and install command automatically.

### 6. Commit and push

```bash
git add -A
git commit -m "Release v1.0.7-beta.1: <one-line summary>"
git push origin main
```

Wait for [CI](../../.github/workflows/ci.yml) to pass on `main` before tagging.

### 7. Tag — this triggers the release

```bash
git tag -a v1.0.7-beta.1 -m "v1.0.7-beta.1 — Beta Release"
git push origin v1.0.7-beta.1
```

The pipeline then:

1. **validate** — parses the channel from the tag, asserts every manifest declares
   that exact version, and requires matching `CHANGELOG.md` / `RELEASE_NOTES.md` entries.
2. **verify** — builds the C engine and runs the full test suite on Linux and macOS.
3. **tarballs** — builds `vapor-ram-v<version>-linux-x86_64.tar.gz` and
   `-macos.tar.gz` natively on each runner.
4. **build-dist** — builds the sdist and wheel, runs `twine check`, and asserts the
   artifact version matches the tag.
5. **github-release** — creates the release with the correct prerelease flag; only
   Stable is marked `--latest`.
6. **pypi-publish** — uploads via OIDC Trusted Publishing with PEP 740 attestations.
   No API token is stored.
7. **docs** — **Stable only.** Rewrites the `<!--VERSION-->` markers across
   `docs/index.html`, `docs/releases.html` and `docs/changelog.html`, verifies no
   other version string survives on any of them, and pushes — refreshing GitHub
   Pages. A prerelease skips this job entirely, which is how the site stays
   pinned to stable while the releases page continues to list every build.

### 8. Verify

```bash
gh run watch <run-id> --exit-status          # all jobs must be green
gh release view v<version> --repo sudsarkar13/vapor-ram
pip index versions vapor-ram --pre
```

Then install the **published** artifact — not your local build — in a clean
venv. This is what caught a completely broken wheel at v1.0.7-alpha.4, which
every CI job had passed:

```bash
python3 -m venv /tmp/verify && /tmp/verify/bin/pip install "vapor-ram==<version>"
/tmp/verify/bin/vapor --version
/tmp/verify/bin/vapor presets                # personas load from disk
/tmp/verify/bin/vapor inspect --dir <path-to-model-dir>   # real GGUF geometry
/tmp/verify/bin/vapor serve --port 8901 --no-auth --no-preload &
curl -s localhost:8901/health | python3 -m json.tool      # derived weights format
curl -s -o /dev/null -w '%{http_code}\n' localhost:8901/  # dashboard serves
```

**After a stable release, check the site.** The `docs` job runs only on stable,
so this is the one time the pages move:

```bash
git fetch origin main && git log origin/main --oneline -2   # docs commit, if any
```

Open [the site](https://sudsarkar13.github.io/vapor-ram/) and confirm the nav
badge on **all three pages** names the new stable version, and that the releases
page still lists prereleases under its filter. If the badge shows a prerelease,
something bypassed the channel gate — treat that as a release bug.

> The `docs` job legitimately makes **no commit** when the pages already carry
> the tag (it exits 0 with "Docs already current"). A green job with no commit
> is not a failure.

## 🔁 Re-running a failed release

The workflow is idempotent: it updates an existing release rather than erroring.
Re-run it from the Actions tab, or:

```bash
gh workflow run release.yml -f tag=v1.0.7-beta.1
# add -f skip_pypi=true if that version already uploaded successfully
```

PyPI refuses re-uploads of an existing version — use `skip_pypi` when only the
GitHub Release needs repairing.

## 📦 Packaging notes

Python modules live in `vapor_ram/`. Runtime assets (dashboard, presets, tools,
compiled engine) live at the repository root and are staged into the package at
build time by `setup.py`'s `build_py` override — they are **not** committed under
`vapor_ram/` and are gitignored there.

Both the sdist and the wheel are gated in CI for completeness. After any change
to the packaging, verify a real install rather than trusting the build log:

```bash
python -m build --wheel
pip install --force-reinstall dist/*.whl
vapor --version && vapor presets      # must list the disk-defined personas
vapor serve --port 8901 &             # then curl the dashboard and a JS chunk
```
